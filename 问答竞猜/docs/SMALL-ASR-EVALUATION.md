# B23 · 固定 small 模型评估：中文候选仍未达标

结论：这次固定模型评估完成，中文自动候选验收没有通过。原两条 WAV 字节不变，small 的一条转写与预设文字仅有繁简字形差异，另一条仍不符合预设文字；现有保守匹配器均返回空候选。默认仍是 tiny，small 仅作为显式模型档案可选，不自动升级或生产启用。

| 预设合成文字 | tiny 实际转写 | small 实际转写 | small 游戏候选 |
| --- | --- | --- | --- |
| 我选择第三项。 | 無選擇第三項 | 我選擇第三項 | 空 |
| 答案是三。 | 大十三 | 答案13 | 空 |

第一项是明确的繁体表达兼容缺口，不能与第二项的转写错误混为一谈。这里按预设合成文字评估；没有人工听音，所以也不把两句结果当作真人中文识别准确率或独立的合成发音验收。没有把“13”或否定句解释成第三项，没有修改生产匹配器来提高表面命中率。

## 确认与准确率分开记录

两种模型都实际经过 Spring HTTP → Java → 单个私有 ASR worker。中文四条测试都运行到：空候选 → 会话版本/分数不变 → 独立手动选择 C → 明确确认后100分。随后 small 的两条正向准确率断言仍失败，JUnit 明确保留2项失败；tiny 按历史已知空候选回退合同验证，2项通过。两模型的同一英文固定音频都正确形成 C 候选，确认前0分、确认后100分。

不能把“手动确认成功”写成“中文自动候选通过”，也不能把普通CI默认跳过的原生模型测试计为通过。两次模型评估合计8个原生JUnit用例：6通过、2失败；其中队列用例验证边界与记录测量，不要求所有请求成功。

身份、题包、配额和游戏时钟均为 test profile 合成数据；真实模型推理、HTTP传输与Java的4秒传输期限实际执行。未接真实账户或真实麦克风。

## 最终单次资源与排队观测

ASR CPU int8、2计算线程、1 worker；两个模型顺序运行，没有同时占用。模型进程RSS每40ms采样，3GiB停止线未触发，最终全部进程退出。采样峰值是 small 617,103,360字节（约589MiB），tiny 239,214,592字节（约228MiB）；不包含整个JVM/宿主内存，也不等同内核精确瞬时峰值。

| 测量情境 | small 端到端耗时/结果 | tiny 端到端耗时/结果 |
| --- | --- | --- |
| 串行两条 | 1.727 / 1.504秒，均返回文本 | 0.371 / 0.273秒，均返回文本 |
| 同一Java客户端同时2条 | 1.549 / 3.106秒，均返回文本 | 0.555 / 0.278秒，均返回文本 |
| 同一Java客户端同时4条 | 2条完成，2条立即 ASR_BUSY | 2条完成，2条立即 ASR_BUSY |
| 两Java客户端共4条，共享一个ASR进程 | 2条完成（1.535 / 2.977秒），2条约4.003秒超时 | 4条均返回文本，0.289–1.113秒 |

“返回文本”不是“正确候选”。表中时延包含排队和传输，未单独测服务端队列等待时间。原 Java 每客户端容量2、4秒传输期限和 worker 配置backlog4均保持不变。约3ms的超时调度开销不是放宽协议到5秒；测试使用5秒上限仅用于检测4秒取消加调度开销失控。请求超时不能保证模型计算立即中断，本次关闭worker会结束残余工作。

这只是固定机器、两条短合成音频和有限请求的一次比较，不能外推多人商用吞吐、长时稳定性或跨实例全局配额。small 在四请求共享队列下已出现超时，不应据此默认承诺CPU多人低延迟。
